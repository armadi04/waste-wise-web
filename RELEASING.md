# Releasing

Nestplate Starter (backend + frontend) is released **automatically** by
`semantic-release` from your Conventional Commit messages — you never tag it by
hand.

| Scope | Tag pattern | How it's cut | What a merge to `master` triggers |
|-------|-------------|--------------|---------------------------------|
| **App** (backend + frontend) | `v*` (e.g. `v1.2.0`) | **auto** — semantic-release on merge to `master` | a `v<version>` tag + a GitHub Release ([`release.yml`](./.github/workflows/release.yml)) |

The backend and frontend version together under one tag. They ship as one
product, so a split scheme would only create ambiguity about which pair is live.

Deployment is deliberately **not** wired into the workflow — how the app is
deployed is a separate concern.

## App release (`v*`) — automated, commit-driven

You don't tag the app. When commits land on `master`,
[`release.yml`](./.github/workflows/release.yml) runs `semantic-release`, which
reads every Conventional Commit since the last release and:

1. picks the next [SemVer](https://semver.org) version,
2. creates the `v<version>` git tag,
3. cuts a GitHub Release whose notes are generated from those commits.

Nothing is committed back to `master` — the notes live on the Release, so the
history stays free of `chore(release)` bot commits, and the repo carries no
`CHANGELOG.md` to keep in sync. The Releases page *is* the changelog.

### What your commit message does

| Commit | Version effect |
|--------|----------------|
| `fix: …` | **PATCH** — `v1.0.0` → `v1.0.1` |
| `feat: …` | **MINOR** — `v1.0.0` → `v1.1.0` |
| `feat!: …` or a `BREAKING CHANGE:` body line | **MAJOR** — `v1.0.0` → `v2.0.0` |
| `docs/style/test/chore/ci/wip: …` | **no release** |

```bash
# breaking change — note BREAKING CHANGE in the body, not the subject:
git commit -m "feat(users): return paginated results from GET /api/users

BREAKING CHANGE: the endpoint now returns { data, meta } instead of a bare array"
```

A lazy message (`update`, `fix`, `asd`) means the machine can't read your intent
and the version won't bump — discipline in commits is what makes the release
automatic.

### Checking what your commits would release

```bash
bun add --no-save semantic-release conventional-changelog-conventionalcommits
GITHUB_TOKEN=dummy bunx semantic-release --dry-run --no-ci
rm -rf node_modules package.json   # both are git-ignored at the root
```

Nothing is published in `--dry-run`; it prints the version it *would* cut. There
is no root package manager workspace, so the tooling is installed with
`--no-save` and removed afterwards.

## How the in-app changelog is fed

The app shows its own release notes at `/changelog`, read at runtime rather than
bundled. `GET /api/changelog` (`backend/src/changelog/`) calls the GitHub
Releases API and returns each release's notes verbatim; the page concatenates
them and parses them with `frontend/src/lib/utils/changelog.ts`. A release body
is generated by the `conventionalcommits` preset, so its format is fixed — a
change to that format means updating the parser and its tests too.

The token stays server-side, so set `GITHUB_REPO` (defaults to
`univSTEKOM/nestplate`) to point at your own fork. `GITHUB_TOKEN` is optional
for a public repo — it lifts the anonymous rate limit — and **required** for a
private one, which otherwise renders the page empty. Responses are cached for
ten minutes, so a new release can take that long to appear.

The endpoint is behind `JwtAuthGuard` with no permission check: release notes
are for every signed-in user, which is why the sidebar entry is ungated too.

### Commit subjects are published to users

`feat` and `fix` subjects appear verbatim on `/changelog`. Write the
user-visible outcome rather than the implementation, and pick a scope that maps
to a friendly module name in
`frontend/src/lib/constants/changelog-labels.ts` — otherwise the page shows the
raw scope.

## Branch flow

Releases are cut on **`master`** only. Work flows `feat/* → master`; the `v*` tag
happens when a change reaches `master`.

## Database migrations

Production boots with `synchronize` off and applies pending migrations
automatically, so a release that touches an entity **must** ship its migration
in the same commit. Review the generated SQL before merging — a migration that
renames or drops a column runs unattended on deploy.

## Conventions

- Tags are immutable once created — never re-point a published tag.
- Release notes come from commit messages — write them for the changelog reader.
- Commit messages follow `type(scope): description`.
